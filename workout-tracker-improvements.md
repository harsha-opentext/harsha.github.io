Workout Tracker — Improvements & Feature Backlog

Bugs & Broken Behaviour
1. ⭐ 👤 Template editing changes do not persist — User-reported as confirmed broken. Code paths exist for a full-array PUT to workout-data/templates.json, but changes are not being reflected. Investigate whether the save is firing, whether the SHA is stale causing a silent 409, or whether the component's local state is not being committed back to the service before the write. (My note: when I say template editing is broken, I do not actually mean the actual template editing in the session template section. I mean when I am applying the session template today and I make a change during that apply process. You can ask clarification if you need.)
2. 🔴 👤 Session history is entirely read-only — no edit path exists — The history page has no in-place edit UI. The only way to "edit" a past session is the "Use as Template" shortcut, which navigates to /workout/log and creates a new session rather than overwriting the original. Past session edits never reach GitHub. Needs a dedicated edit flow that overwrites the correct workout-data/YYYY-MM-DD.json file.
3. 🔴 👤 Workout history refresh may show stale data — loadHistory() calls the GitHub Contents API to get a directory listing of workout-data/, which is subject to caching. Validate whether the directory listing reflects recent writes, or whether a cache-busting strategy (e.g. adding a timestamp query param or checking ETag) is needed. Also confirm that newly saved sessions appear in the list without a manual page reload.
4. 🔴 👤 Volume calculations are incorrect for certain exercises (e.g. close grip bench press) — Current formula is sum(reps × weightKg) per workout entry per session. For bilateral compound lifts where the user may be logging one-side weight (e.g. dumbbell variations), the volume will be halved. Investigate whether the formula needs a multiplier per exercise type, or whether a per-workout "weight mode" flag (total vs per-side) should be introduced. Audit existing analytics charts for this inconsistency. (Mynote: ignore this for now and wait for me to identify the issue)
5. 🔴 👤 Volume calculation logic is undocumented and unvalidated — The definition of volume (reps × weightKg aggregated per session) is embedded in multiple places (WorkoutAnalyticsService.computePerSessionStats, WorkoutHistoryComponent.entryVolume) without a shared utility function. There is no explanation in the UI about what "volume" means. Centralise the formula into a shared utility, add a source-of-truth definition, and surface the definition to the user.

UX & Quality-of-Life Fixes
1. 🟡 👤 Default gym name save is silent — no visual confirmation — The 250ms debounce save to GitHub works mechanically, but there is zero feedback to the user (no spinner, no "saved" indicator, no error state if the save fails). Add a saving/saved/error signal badge next to the field, mirroring the pattern used in calorie settings.
2. 🟡 👤 Session start time is not auto-populated when applying a template — When a session is started via a template, startTime is left undefined until the user manually fills in the time input. The session start time should be captured automatically as new Date() at the moment the template is applied and the session begins, while remaining editable afterward.
3. 🟡 👤 Set completion tracking is absent during live sessions — When following a template or building a session, there is no way to mark a set as "done" in real time. During a workout the user needs to cross out or check-off completed sets mentally. Add per-set checkmark toggles (visual state only, not persisted) so users can track progress mid-session without confusion.
4. 🟡 Workout history filter options are limited — Current filters are All, Yesterday, Last Week. There is no filter by muscle group, no filter by specific exercise, no custom date range, and no way to see all sessions in a given month. Expand filtering to match the richness of the calorie history page.
5. 🟡 👤 Exercise selection during a session shows no historical context — When a user adds an exercise to a session (or sees one pre-filled from a template), there is no "last time you did this: 3×80kg" display. The user has to navigate away to analytics to see past performance. Show the most recent session stats for that exercise inline within the session log view.
6. 🟡 👤 Cardio workouts are treated identically to resistance training — There is a cardio muscle group enum value but no special handling. For cardio, the relevant metrics are duration and distance (or calories burned), not reps and weightKg. Sets/reps/weight fields are meaningless for a treadmill run. Introduce a WorkoutType discriminant (resistance | cardio) on Workout, and render appropriate inputs per type in the session log.(mynote: evaluate how this affects the csv import and handle elegantly)

New Features
1. 🟢 👤 Rest timer / workout timer with intuitive integration — A configurable rest timer that starts automatically after a set is marked complete (see item 8). Should feel native: a persistent bottom-of-screen countdown that appears after a set tap, with a subtle vibration/alert on expiry. The timer should not require navigating to a separate screen. Also consider a total elapsed session timer visible at the top of the session log page.
2. 🟢 👤 5-star rating for individual workouts (per-exercise), alongside existing session mood rating — The session already has a mood (1–5) rating. Add an optional per-SessionEntry rating (e.g. "how did this exercise feel?") stored as a numeric field on SessionEntry. Display aggregate per-exercise feel scores in analytics alongside volume and weight progression.
3. 🟢 👤 In-app feature request / feedback submission — A persistent, low-friction way to submit feature requests or bug reports from anywhere in the app. Tapping a small FAB or long-pressing a specific UI element opens a text input that stores the submission to GitHub (e.g. appended to a workout-data/feedback.json file). Investigate shake-to-open gesture support via the DeviceMotionEvent API (requires https and user permission on iOS/Android).
4. 🟢 Superset / circuit support — Allow two or more exercises to be linked as a superset within a SessionEntry. Linked exercises appear as a group in the session log and their volume is calculated together. Useful for antagonist pairings (e.g. bicep curl + tricep extension). (Mynote: hold off on this for now)
5. 🟢 Progressive overload suggestions — After loading historical data for an exercise, surface a simple recommendation: "Last session: 4×80kg. Try 4×82.5kg today." Based on the last logged session for that exercise. Show as a subtle suggestion chip next to the exercise, dismissible.
6. 🟢 Personal record (PR) detection and celebration — When saving a session, compare maxWeight for each exercise against all historical sessions. If a new max is set, show a celebratory notification (or inline badge) and log it. Store PR data as a derived cache for fast access. (Mynote: hold off on this until we figure out a way where we don’t need to traverse through all data files to calculate it)
7. 🟢 Warm-up set tagging — Allow individual sets to be tagged as warmup: true. Warm-up sets are excluded from volume calculations and analytics. Add a small tag button per set row in the session log.
8. 🟢 1-Rep Max (1RM) calculator / display — Using the Epley formula (weight × (1 + reps / 30)), compute an estimated 1RM for each exercise and show it in analytics. No new data entry required — derived from existing set data. 
9. 🟢 Duplicate / clone a past session — From workout history, add a "Repeat this session" action that pre-fills the session log with the same exercises and last-used weights (not copying the date), letting the user start from a known baseline without going through templates.
10. 🟢 Session notes field — A free-text notes field at the session level (e.g. "felt fatigued, gym was crowded"). Stored in Session.notes?: string. Shown in history and considered for analytics context.
11. 🟢 Weekly workout summary — A brief auto-generated summary at the end of each week: total sessions, total volume, muscles trained, PRs set, vs weekly target. Surfaced on the Workout Hub tile or as a notification.
12. 🟢 Muscle group training frequency / balance chart — A radar or bar chart in analytics showing how many sessions each muscle group was trained in a given period. Helps identify imbalances (e.g. chest trained 4× more than back).
13. 🟢 Body measurements tracking — Beyond daily body weight, allow logging of body measurements (chest, waist, hips, arms, thighs) on the workout or calorie side. Stored as a separate entry type with a date.
14. 🟢 Exercise search and filter in session log — When adding an exercise to a session, a full search/filter input to find workouts by name or muscle group, instead of scrolling a flat list.
